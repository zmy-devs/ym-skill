# 审查与修复

实现完成后必须执行。下面的检查表是各专项规则的审查索引，不代替读取当前技术栈对应资料。

## 确认范围与模式

- 写代码后的自审、用户要求审查并修复：直接修复本次范围内的问题，不停在问题列表。
- 用户只要求审查或明确禁止修改：只读检查，给出问题和依据；不因发现严重问题擅自写文件。
- 有 diff 时检查最终 diff 和任务内新文件，同时读取受影响的完整函数、组件与直接调用方；没有 diff 时检查用户指定代码。无法确定审查对象且没有可用改动时，先要求补充范围，不宣称审查完成。
- 只加载匹配框架、样式和组件库的资料。每项在内部标记通过、已修复、不适用或受阻；不适用不是通过，未运行验证不是验证成功。

## 严重程度

| 等级     | 判断依据                                                        | 处理                                   |
| -------- | --------------------------------------------------------------- | -------------------------------------- |
| Critical | 有证据的安全漏洞、敏感信息泄露、不可逆数据损坏等                | 可写模式先修复，未解决不得标记通过     |
| High     | 构建/类型失败、关键交互不可用、错误状态或数据写入、核心功能回归 | 可写模式必须修复并验证后才可通过       |
| Medium   | 职责混杂、复杂控制流、无意义抽象、重复实现等维护问题            | 本次范围内按规则修复，避免引入更大改动 |
| Low      | 命名、空行、注释、默认属性等个人风格                            | 按项目配置修正，不扩大改动范围         |

等级取决于实际后果，不按关键词机械判定；嵌套三元或多一个 wrapper 不自动等于 High。未运行的验证说明覆盖缺口，不凭空推断为代码缺陷。

## 修复、复查与验证

1. 先根据实际后果处理 Critical / High，再修复范围内的结构与风格问题。每项修改保持原有需求和调用契约；发现规则不适用时说明理由，不为了打勾改坏代码。
2. 重新读取修复后的最终代码和 diff，复查对应问题、直接受影响行为及是否引入新问题；不能拿修复前的检查结果充当最终结果。
3. 根据改动运行项目已有的格式检查、lint、类型检查、相关测试或构建。选择能覆盖实际风险的检查，不强制每次跑完整全仓流水线，不为低影响风格改动新建测试体系。
4. 交互变更在可用的运行环境核实关键路径；无法实际运行时，写明哪些判断仅基于静态检查。记录命令、成功/失败和未执行原因；既有无关失败与本次引入的问题分开说明。
5. 修复引起代码变化后重跑受影响的检查；已通过且没有新变化时停止重复验证。可修复问题未解决则继续；重复遇到同一外部阻塞时停止盲目重试，明确状态为未通过或部分验证。

## 结果输出

实现/修复模式简短附上以下信息，内容填实际结果，不必输出完整检查表：

```text
审查结果：通过 / 未通过 / 部分验证
已修复：具体问题；没有则写“无”。
验证：实际执行的命令与结果；未执行项及原因。
遗留：未解决的问题、等级和位置；没有则写“无”。
```

- “通过”要求范围内已知问题已处理、必要检查已通过；缺少必要运行验证时用“部分验证”，已知 Critical / High 未解决时用“未通过”。
- 仅审查时先列有证据的问题：`[等级] 文件:行号 — 触发条件、影响和建议`，按严重程度排序；随后给实际验证和覆盖缺口。没有发现问题时直说“未发现范围内问题”，不要编造 Fixed 或承诺绝对无问题。
- 范围外的既有问题只在确实影响本次任务时记录，不借自审扩展成全仓重构。
