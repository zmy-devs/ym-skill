# 组件设计与组件库

适用于 React 和 Vue；使用哪种组件库就遵循哪种库的实际实现，不因规范提到 shadcn/ui 而安装它。

## 划分职责

- 页面编排业务场景，业务组件封装领域交互，基础 UI 保持可组合；不让页面同时承担全部请求、数据转换、状态管理和 UI 细节。
- 当一段 UI 有独立职责、重复业务配置或复杂状态时抽组件、Hook / composable 或 service；不为短小的一次性静态结构创造多层包装。
- 先查项目已有组件、数据层和工具，避免重复实现搜索、选择、空状态、焦点与弹层能力。

## 公共业务组件与 API

- 跨场景复用的业务封装默认放 `components/common/`；已有目录约定优先。只属于一个页面或功能的组件留在对应功能目录，不把所有组件搬进 common。
- 用 `LocaleSelector`、`ResourcePicker`、`SearchInput` 等名称表达真实职责；文件名仍遵循通用命名规则，如 `locale-selector.tsx`。
- 业务组件提供少量与业务有关的输入、选中值和事件，内部处理领域映射、UI 组合、过滤、空状态和错误展示；数据获取归属沿用项目架构，不强迫所有选择器自己请求接口。
- 不让每个页面重复传 `renderItem`、`getLabel`、`filterFunction` 和大量底层配置来拼同一业务场景。一次性配置应留在业务封装内部。
- 通用基础组件为了真实的跨场景组合可以提供 render prop、slot、泛型和配置接口；不能把业务组件的收敛规则变成禁止所有可扩展 API。
- 不把复杂 props 改成隐式全局状态，也不为了看起来简单隐藏必要的受控值、加载状态或错误处理。

```tsx
<LocaleSelector value={locale} onValueChange={handleLocaleChange} />
```

示例表达业务 API，不要求零参数组件；是否受控取决于项目的数据所有权。

## shadcn/ui 与 primitive

- 已使用 shadcn/ui 时，优先复用本地已有组件和能力。先检查项目版本、底层实现及其 API，不照搬不同版本或不同底层库的示例。
- 页面中同一业务选择器、复杂搜索框或弹层流程反复组合大量 primitive 时，封装成业务组件，让页面只保留业务输入和事件。
- 少量、一次性且清楚的 primitive 组合可以留在使用位置；不要为了禁止页面出现 `DialogContent` 或 `ComboboxItem` 而再套一层透传壳。
- 封装时保留可访问名称、键盘操作、焦点管理、受控协议及必要的 ref / 事件传递，核对最终 DOM，避免交互元素嵌套。

## Dialog / Sheet 单实例

- 同一列表中同一种、同一时刻只操作一条记录的详情/编辑 Dialog 或 Sheet，放在循环外，只保留一个实例，通过选中项或选中 ID 和打开状态控制内容。
- 不在 `items.map(...)` 或 `v-for` 中给每条记录创建同功能的完整 Dialog / Sheet；每行可以保留轻量触发按钮。
- 打开时内容对应当前选中项，切换对象不复用错误草稿；删除、刷新、关闭和异步完成后不会操作旧记录。根据组件卸载/动画行为在合适时机清理选中状态。
- 用户确实需要同时存在的独立弹层，或组件库的组合、焦点恢复契约另有要求时，按真实交互设计；不为合并实例破坏触发器可访问性或关闭后焦点恢复。
- 改为受控单实例时，实际验证打开、切换、取消、保存、关闭后的焦点及失败状态；不能只看代码是否移到了循环外。

技术参考：[shadcn/ui Button](https://ui.shadcn.com/docs/components/button)、[shadcn/ui Dialog](https://ui.shadcn.com/docs/components/dialog)。具体 API 以仓库本地组件为准。
